## 1. 目的与适用范围

本规范用于解决两个 AI Agent 共用同一个本地工作区时的 Git 风险：

1. 两个 Agent 同时执行 `git add`、`commit`、`push` 等写操作，造成索引、提交或远程状态互相覆盖；
2. 一个 Agent 把另一个 Agent 尚未提交的修改一起暂存或提交；
3. 推送前未检查远程更新，造成非快进推送或覆盖；
4. 把密钥、字幕、学习记录、数据库或日志提交到仓库；
5. 用强制推送、硬重置、删除文件等方式“解决”问题，造成不可恢复的损失。

本规范适用于 SceneLingo 仓库内的所有 Git 操作，包括本地提交、远程同步、分支操作、标签和发布。

## 2. 角色与文件所有权

### 2.1 职责分工

| 角色 | 主要职责 | 默认可写范围 | 不应擅自做的事 |
| --- | --- | --- | --- |
| **Claude Code** | 需求分析、系统架构、数据库/API 设计、任务拆分、设计评审、工程学习文档 | `docs/` 中的需求与设计文档、`tasks/`、设计评审报告 | 不实现应用代码；不修改 `app/`、`tests/`，除非用户明确授权 |
| **Codex CLI** | 按已批准任务卡实现代码、编写和执行测试、修复缺陷、提交开发报告 | `app/`、`tests/`、实现报告、测试执行记录 | 不重写需求/架构文档；不扩大范围；不擅自改变已批准设计 |
| **用户** | 确认需求、批准范围和方案、最终验收、裁决冲突 | 全部 | 对提交/推送拥有最终决定权 |

### 2.2 共享文档

- `docs/05-测试与验收.md` 为共享文档：Claude Code 负责验收标准和测试计划，Codex CLI 负责追加实际测试结果；双方都不得覆盖对方已写内容。
- `docs/06-项目变更记录.md` 记录经用户确认的变更；由执行该变更的 Agent 追加，必须注明日期、原因、影响和批准人。
- `docs/07-Git协作与版本管理规范.md`（本文）是协作规则；任何修改都必须先经用户确认，任一 Agent 不得单方面改写。
- `CLAUDE.md`、`AGENTS.md` 是角色说明；修改必须经用户确认，且不得用来绕过本规范。

### 2.3 所有权不等于覆盖权

即使某个文件属于自己职责范围，也不得覆盖另一个 Agent 尚未提交的修改。发现工作区有非自己产生的改动时，先停止并报告，不得用保存、暂存、提交、还原或清理的方式处理。

## 3. 单写者原则：禁止并发 Git 写操作

### 3.1 原则

**同一时刻只允许一个 Agent 执行 Git 写操作。** 两个 Agent 共用同一个工作区、同一个 `.git` 目录和同一个索引，Git 本身不是为并发写入设计的；并发执行会导致索引锁、半暂存状态、提交内容混淆或远程覆盖。

### 3.2 什么是 Git 写操作

以下操作视为 Git 写操作，必须纳入单写者约束：

- 修改工作区或索引：`git add`、`git rm`、`git mv`、`git restore`、`git checkout`（涉及文件时）、`git switch`；
- 创建提交或引用：`git commit`、`git commit --amend`、`git tag`、`git branch`、`git branch -d/-D`；
- 改写历史或工作区：`git reset`、`git rebase`、`git merge`、`git cherry-pick`、`git revert`、`git stash`、`git clean`；
- 远程写操作：`git push`、删除远程分支/标签；
- 会更新远程跟踪引用的同步操作：`git fetch`、`git pull`；
- 任何会改变 `.git/index`、`.git/refs`、`.git/HEAD` 或工作区文件的操作。

只读操作（`git status`、`git diff`、`git log`、`git show`、`git remote -v`、`git ls-files`）可以在不修改状态的前提下使用；但读取结果后如果发现另一个 Agent 正在写入，仍应等待。

### 3.3 开始前的检查

任何 Agent 在开始 Git 写操作前，必须执行并记录：

```bash
git status --short --branch
git log -1 --oneline --decorate
git remote -v
```

判断规则：

- 若出现非自己产生的已修改/已暂存文件：**停止**，报告文件列表，等待用户协调；不得暂存、提交、还原或 stash。
- 若另一个 Agent 正在同一工作区操作：**停止**，等待其报告完成。
- 若无法确认工作区状态：**停止**，不要“先提交再说”。

### 3.4 完成后的交接

- 执行 Git 写操作的 Agent 必须在报告中说明：操作开始/结束、提交哈希、是否推送、工作区是否干净。
- 下一个 Agent 只能在收到“上一个 Agent 已完成”的明确信息后开始写操作。
- 用户是并发冲突的最终协调者；Agent 不得自行假设“另一个 Agent 已经结束”。

### 3.5 共用工作区的暂存规则

- 禁止 `git add -A`、`git add .`、`git commit -a`。
- 只暂存本次工作单元明确涉及的文件，使用显式路径：

```bash
git add -- "path/to/file1" "path/to/file2"
```

- 禁止用 `git add -f` 绕过 `.gitignore` 添加被忽略的文件；确需提交时先取得用户明确授权并说明原因。
- 提交前必须检查 `git diff --cached --name-status`，确认没有夹带其他 Agent 的文件。

## 4. 工作单元、提交与分支

### 4.1 工作单元

一个“工作单元”应满足：

1. 有明确目标（对应需求、设计、任务卡或用户指令）；
2. 已经过用户验收，或用户明确同意进入提交阶段；
3. 可以独立说明改了什么、为什么改、如何验证；
4. 不把无关修改混在一起。

### 4.2 提交规则

- **每个经过验收的工作单元一个独立 commit。**
- 一个 commit 只做一个逻辑变更；不要把“文档 + 代码 + 格式化 + 无关修复”混在一起。
- 需求/架构文档与代码/测试默认分开提交；如果用户要求同一工作单元合并提交，必须在提交说明中写明并经用户同意。
- 未验收的工作不提交；未完成的半成品不以“WIP”形式推送到 `main`。
- 提交后、推送前必须通过第 6 节的安全检查。
- 提交由实际修改该工作单元的 Agent 执行；如果用户指定另一个 Agent 提交，必须先确认没有并发写，并由该 Agent 重新检查工作区。

### 4.3 分支策略

- 个人项目默认在 `main` 上按工作单元提交，保持历史简单。
- 较大或高风险改动可使用短生命周期分支；分支合并必须经用户同意，并优先使用快进合并。
- 不使用长期分叉；不删除未合并分支；不删除远程分支或标签，除非用户明确授权。

### 4.4 提交信息

格式：

```text
<type>(<scope>): <summary>

<为什么改、改了什么、如何验证>

Refs: <需求/任务/文档编号，可选>
```

常用 type：

| type | 用途 |
| --- | --- |
| `docs` | 需求、架构、设计、规范、学习笔记 |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `test` | 测试代码或测试数据 |
| `refactor` | 不改变行为的重构 |
| `chore` | 工具、配置、依赖等杂项 |

要求：

- summary 使用祈使语气，简洁说明结果，不超过约 72 个字符；
- 不使用 `update`、`changes`、`fix stuff` 等无法判断内容的说明；
- 正文写清楚验证方式和已知限制；
- 不伪造测试结果、提交者或共同作者。

示例：

```text
docs(git): add Git collaboration and version management policy
feat(subtitle): add SRT import and cue validation
test(review): cover mastery rules across distinct dates
```

## 5. 提交前检查

在 `git commit` 之前，执行以下检查并记录结果。

### 5.1 工作区

```bash
git status --short --branch
git diff
```

确认：

- 只有本次工作单元涉及的文件发生变化；
- 没有另一个 Agent 的未提交文件；
- 没有意外的 `docs/01`、`docs/02`、`docs/03`、`app/`、`tests/` 修改（除非本次工作单元明确包含）；
- 没有 `.DS_Store`、缓存、日志、数据库、字幕等被忽略文件混入。

### 5.2 暂存内容

```bash
git add -- <明确路径>
git diff --cached --name-status
git diff --cached
```

确认：

- 暂存列表与报告中的文件列表一致；
- 没有夹带其他文件；
- 没有删除不该删除的文件；
- 没有把整段无关格式化或重排混入。

### 5.3 格式与基本质量

```bash
git diff --cached --check
```

- 文档：链接、标题层级、表格、代码块可读；不出现无法解释的占位符。
- 代码：按项目测试要求运行测试；测试失败不得声明完成。
- 不把“未运行测试”写成“测试通过”。

### 5.4 安全扫描

按第 7 节执行敏感信息检查；未通过不得提交。

## 6. 推送前检查

推送是独立关卡：**提交完成不等于可以推送。** 推送前必须重新检查。

### 6.1 检查工作区

```bash
git status --short --branch
git log -1 --stat
```

确认：

- 工作区没有未提交的意外修改；
- 最新提交就是本次工作单元；
- 提交内容与用户验收的内容一致。

### 6.2 检查远程更新

```bash
git fetch origin
git status --short --branch
git log --oneline --left-right HEAD...origin/main
```

判断：

- 若远程没有新提交：可以继续检查并推送；
- 若远程有新提交（本地落后）：**停止**，报告远程提交；不得自行 `merge`、`rebase` 或 `push --force`；
- 若本地与远程分叉：**停止**，由用户决定合并方式；
- 若远程地址不是 `https://github.com/iseukrbrvidjrh-arch/-3.git`：**停止**，先确认远程配置。

### 6.3 检查提交内容

```bash
git show --stat --oneline HEAD
git show --name-status --format=fuller HEAD
```

确认：

- 提交者/提交说明正确；
- 文件列表与验收范围一致；
- 没有密钥、个人数据、字幕、数据库、日志或大文件；
- 没有误删文件；
- 没有把另一个 Agent 的提交一起推送（如果存在，先报告）。

### 6.4 推送

只允许快进推送：

```bash
git push origin main
```

禁止：

- `git push --force`
- `git push --force-with-lease`
- `git push --mirror`
- 删除远程分支/标签
- 用推送“覆盖”远程历史

推送后检查：

```bash
git status --short --branch
git log -1 --oneline --decorate
```

报告中写明：推送是否成功、提交哈希、远程分支、仍存在的风险。

## 7. 敏感信息与个人数据

### 7.1 禁止提交的内容

以下内容不得提交，除非用户明确授权且已采取脱敏措施：

- API Key、访问令牌、密码、私钥、证书；
- `.env`、`.env.*`（`.env.example` 仅允许占位符）；
- `.secrets/`、`secrets.*`、`credentials.json`；
- `*.pem`、`*.key`；
- SQLite 数据库及 WAL/SHM 文件；
- `data/`、`records/`、`learning_records/`、`exports/`；
- 用户字幕 `*.srt`、`*.vtt` 及未经授权的影视字幕样本；
- `logs/`、`*.log`、包含密钥或个人数据的截图；
- 含个人邮箱、电话、住址、账号等个人数据的文件；
- 大体积二进制文件、缓存、`.DS_Store`。

`.gitignore` 是基础护栏，不是唯一检查；提交前仍需人工检查暂存内容。

### 7.2 扫描建议

高信号模式扫描（仅用于发现真实密钥，不把规范中的说明词当泄露）：

```bash
git diff --cached | grep -nEi \
  'sk-[A-Za-z0-9_-]{20,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|xox[baprs]-|AIza[0-9A-Za-z_-]{35}|BEGIN [A-Z ]*PRIVATE KEY'
```

同时人工查看：

```bash
git diff --cached --name-status
git diff --cached
```

- 如果命中只是文档中的“API Key”“token”等说明词，记录为误报；不得因此跳过人工检查。
- 如果发现真实密钥：**立即停止提交/推送**，报告文件与行号，建议轮换密钥；不得把密钥写进提交说明或聊天记录。
- 如果密钥已经推送：不要自行强制推送或改写历史；立即报告，由用户决定轮换、撤销和后续处理。

### 7.3 提交身份与元数据

- 提交作者/邮箱会进入 Git 历史，并可能被仓库协作者看到。
- 不得擅自修改全局 Git 配置；如用户要求匿名或使用项目专用身份，应先确认再改。
- 现有提交身份如包含个人邮箱，应在报告中说明；是否更换由用户决定。

### 7.4 字幕与版权

- 影视字幕可能受版权保护；未经授权的字幕不得提交到仓库。
- 测试样本应使用自制、公版或已获授权的内容；如必须使用真实字幕，只保留最小片段并取得用户同意。

## 8. 远程同步与冲突处理

### 8.1 同步原则

- 推送前先 `fetch`，确认远程状态。
- 不自动 `pull`；`pull` 可能触发合并或变基，属于写操作，必须经用户同意并在单写者窗口内执行。
- 远程有新提交时，先报告，不自行合并。
- 合并/变基必须由用户确认方式；不得用强制推送“修复”分叉。

### 8.2 冲突

- 发生冲突时停止自动操作，报告冲突文件。
- 不通过覆盖另一 Agent 的文件来解决冲突。
- 由用户确认保留哪一版，或由对应负责人修改后重新提交。
- 冲突解决后重新运行测试和安全检查。

### 8.3 远程拒绝

如果 `git push` 被拒绝：

1. 不要使用 `--force` 或 `--force-with-lease`；
2. 执行 `git fetch origin`，查看远程新提交；
3. 报告本地/远程差异；
4. 等待用户决定合并、变基或放弃本次推送。

## 9. 禁止操作

以下操作在未经用户明确授权时一律禁止：

| 禁止操作 | 原因 |
| --- | --- |
| `git push --force`、`--force-with-lease`、`--mirror` | 覆盖远程历史，可能丢失他人提交 |
| `git reset --hard` | 不可逆丢弃工作区和提交 |
| `git clean -fd`、`git clean -fdx` | 删除未跟踪文件，可能包含另一 Agent 的工作 |
| `git checkout -- .`、`git restore .` | 批量覆盖未提交修改 |
| 对另一 Agent 的修改执行 `git stash` | 擅自移走他人工作 |
| 对已推送提交执行 `git commit --amend` | 改写已发布历史 |
| 对已推送历史执行 `git rebase` | 改写历史，导致协作者分叉 |
| `git filter-branch`、`git filter-repo` | 大规模改写历史 |
| `git rm`、`rm`、删除目录 | 未经授权删除文件 |
| 删除远程分支/标签 | 可能丢失引用 |
| `git add -A`、`git add .`、`git commit -a` | 可能夹带另一 Agent 的文件 |
| `git add -f` 添加被忽略文件 | 绕过安全护栏 |
| `git commit --no-verify` | 绕过检查钩子 |
| 覆盖另一 Agent 未提交的文件 | 直接造成工作丢失 |

**特别规定：不得擅自覆盖另一 Agent 未提交的工作。** 发现冲突时，停止并报告，不用保存、暂存、提交、还原、清理或强制推送的方式处理。

## 10. 标准协作流程

### 10.1 单个工作单元

1. 用户分配工作单元，明确范围和验收标准。
2. Agent 读取相关文档/任务卡，确认自己的文件所有权。
3. 执行 `git status --short --branch`、`git log -1`、`git remote -v`。
4. 若发现另一个 Agent 的未提交修改或并发操作：停止并报告。
5. 只修改自己负责的文件；不覆盖他人未提交内容。
6. 自检：文档检查或测试；记录实际结果。
7. 向用户报告：修改文件、检查结果、风险、建议提交说明。
8. 用户确认验收后，进入提交阶段。
9. 显式暂存本次文件；检查 `git diff --cached` 和 `git diff --cached --check`。
10. 执行安全扫描；有真实密钥则停止。
11. 创建独立 commit。
12. `git fetch origin`，检查远程更新；远程领先或分叉则停止。
13. 检查 `git show HEAD`；确认内容与验收一致。
14. 快进推送 `git push origin main`。
15. 报告提交哈希、推送结果、工作区状态和遗留风险。
16. 下一个 Agent 在收到完成报告后才开始 Git 写操作。

### 10.2 提交与推送分离

- **提交**：用户验收后执行，形成可回退的本地记录。
- **推送**：安全检查通过后执行；提交与推送之间允许暂停。
- 如果安全检查失败，保留本地提交但不推送，修复后由用户确认是否追加提交；不得用强制推送掩盖问题。

### 10.3 跨 Agent 交接

交接报告至少包含：

```text
工作单元：
修改文件：
未提交/已提交状态：
提交哈希：
测试/检查结果：
远程状态：
已知风险：
下一步建议：
```

未提供上述信息，视为交接未完成；下一个 Agent 不应开始写操作。

## 11. 异常处理

| 情况 | 处理 |
| --- | --- |
| 工作区出现陌生修改 | 停止；报告文件；不暂存、不提交、不还原；等待用户 |
| 另一个 Agent 正在提交/推送 | 等待；不执行 `fetch`/`add`/`commit`/`push` |
| 提交前发现夹带文件 | 取消本次提交；用显式路径重新暂存；不删除他人文件 |
| 误提交但未推送 | 报告；用户确认后可用 `git reset --soft HEAD~1` 撤回提交并重新整理；禁止 `--hard` |
| 误提交且已推送 | 报告；用户确认后用 `git revert` 生成反向提交；禁止强制推送/改写历史 |
| 远程领先或分叉 | 停止；报告；由用户决定合并/变基/放弃 |
| 推送被拒绝 | 停止；`fetch` 后报告；禁止强制推送 |
| 发现真实密钥 | 停止；不提交/不推送；报告；建议轮换；已推送则由用户决定处理 |
| 发现字幕/个人数据 | 停止；从暂存区移除；报告；确认是否需要脱敏或改用样本 |
| 测试失败 | 不提交“已完成”；报告失败输出；修复后重跑 |
| 用户取消 | 停止写操作；保留/恢复工作区需用户确认；不擅自清理 |

## 12. 提交前/推送前检查表

### 12.1 提交前

- [ ] 工作单元已经用户验收
- [ ] `git status --short --branch` 无陌生修改
- [ ] 只暂存本次文件，未使用 `git add -A`
- [ ] `git diff --cached --name-status` 与报告一致
- [ ] `git diff --cached --check` 通过
- [ ] 敏感信息扫描通过，或命中仅为误报并已人工确认
- [ ] 文档链接/格式检查，或代码测试通过
- [ ] 提交说明符合规范
- [ ] 没有覆盖另一 Agent 的未提交工作

### 12.2 推送前

- [ ] 最新提交就是本次工作单元
- [ ] `git fetch origin` 后远程无领先提交
- [ ] 本地与远程未分叉
- [ ] `git show --stat HEAD` 内容与验收一致
- [ ] 提交中没有密钥、个人数据、字幕、数据库、日志
- [ ] 测试/检查结果已记录
- [ ] 使用普通 `git push origin main`，未使用任何 force 选项
- [ ] 推送后工作区状态和提交哈希已报告
