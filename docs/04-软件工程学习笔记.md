# 软件工程学习笔记

> 用途：按开发阶段记录软件工程概念、实践过程和认知验收结果，便于回顾与复盘。
> 本笔记使用 SceneLingo 的真实需求与架构作为例子，不替代正式文档。需求基线见 `docs/01-需求规格说明.md`，架构基线见 `docs/02-系统架构设计.md`，数据模型见 `docs/03-数据库设计.md`。

## P1：需求工程（Requirements Engineering）

### 0. 这一阶段到底在做什么

P1 不是“先写一堆功能列表”，而是回答四个问题：

1. 用户到底要解决什么问题？
2. 系统必须做什么，做到什么程度？
3. 哪些事情不做，为什么不做？
4. 怎么证明做出来的东西是对的？

这四个问题分别对应需求获取、需求分析、需求规格说明和需求验证。它们合起来叫 **需求工程（Requirements Engineering, RE）**。

SceneLingo 的例子：

- 用户说“我想通过美剧学英语”——这是**目标（Goal）**，不是功能。
- 用户说“我想把生词加入复习”——这是**用户需求（User Requirement）**。
- 用户说“系统应支持 SRT 和 VTT 导入”——这是**功能需求（Functional Requirement）**。
- 用户说“字幕不能默认上传到云端”——这是**约束/非功能需求（Constraint / Non-functional Requirement）**。
- 用户说“用 SQLite 存数据”——这是**技术方案（Technical Solution）**，不是需求。

需求工程的价值，就是把这些不同层次的话分开，避免把“手段”当成“目的”。

---

### 1. 什么是需求工程（Requirements Engineering）

**定义**：需求工程是系统地获取、分析、记录、验证和维护“系统应该满足什么”的学科与活动。

它通常包括：

| 活动 | 英文 | 在 SceneLingo 中的例子 |
| --- | --- | --- |
| 需求获取 | Elicitation | 阅读立项报告、README，理解用户为什么要在 Mac 本地学字幕 |
| 需求分析 | Analysis | 发现“掌握”没有定义，无法验收；发现“AI 聊天”可能上传整部字幕 |
| 需求规格说明 | Specification | 写成 `FR-065`、`BR-REV-05`、`AC-FR-065-2` |
| 需求验证 | Validation | 让用户确认掌握规则、云端边界、MVP 范围 |
| 需求管理 | Management | 用 `OI-xx` 记录未决问题，用变更记录处理范围变化 |

**关键点**：需求工程不是“项目开始时做一次就结束”。它会持续变化，但变化必须有控制。SceneLingo 用 `docs/06-项目变更记录.md` 记录变更，就是需求管理的一部分。

#### 为什么“需求”不等于“用户说的话”

用户说“我想要一个 AI 聊天”，背后可能是：

- 想快速解释语法；
- 想比较近义词；
- 想让自己写的英文被纠错；
- 想生成短文；
- 或者只是“别人都有，我也要”。

如果直接把它翻译成“做一个聊天框”，就可能做出一个很酷但不解决学习问题的功能。需求分析要追问：**你要完成什么任务？在什么场景？怎样算成功？**

---

### 2. 什么是 SRS（Software Requirements Specification）

**定义**：SRS 是软件需求规格说明书，是对系统“做什么”和“做到什么程度”的正式、结构化、可验证的描述。

它不是：

- 项目立项报告（讲为什么做、值不值得做）；
- 架构设计（讲模块怎么分、技术怎么选）；
- 用户手册（讲怎么操作）；
- 任务卡（讲这一周写什么代码）。

它是：

- 用户、架构师、实现者、测试者之间的**共同基线**；
- 后续设计、开发、测试和验收的输入；
- 需求变更时判断影响的依据。

#### SRS 的常见质量特征

| 特征 | 英文 | 反例 | SceneLingo 的正例 |
| --- | --- | --- | --- |
| 完整 | Complete | 只写“支持字幕”，没写格式和异常 | FR-010、FR-011、BR-SUB-03/04 |
| 一致 | Consistent | 一处说“自动翻译”，一处说“不得上传字幕” | 第 10 节明确发送矩阵 |
| 无歧义 | Unambiguous | “掌握”没有定义 | BR-REV-05 给出 3 日期、7 天、最近成功 |
| 可验证 | Verifiable | “体验要好” | NFR-001 给出可测时间指标 |
| 可追踪 | Traceable | 需求没有编号，测试找不到对应项 | FR → AC → AT 矩阵 |
| 可修改 | Modifiable | 所有内容混在一段话里 | 按模块编号，变更影响清晰 |

#### SRS 与立项报告的区别

| 文档 | 回答的问题 | SceneLingo 例子 |
| --- | --- | --- |
| 立项报告（Project Charter） | 为什么做？值不值得做？大目标是什么？ | 用影视字幕学英语，同时学习软件工程 |
| SRS | 做什么？做到什么程度？怎么验收？ | FR-020 单句按需翻译；AC-FR-020-1 只发送该 cue |
| 架构设计（Architecture Design） | 怎么组织系统？模块和技术怎么选？ | 前端、后端、数据库、AI 调用层如何划分 |
| 测试计划（Test Plan） | 怎么证明？测哪些？ | AT-009 跨日期掌握测试 |

一句话：**立项报告讲“为什么”，SRS 讲“是什么”，架构讲“怎么做”，测试讲“怎么证明”。**

### 3. 功能需求与非功能需求有什么区别

#### 3.1 功能需求（Functional Requirement, FR）

功能需求描述系统**应该做什么**：输入、行为、输出、状态变化。

SceneLingo 例子：

- `FR-010`：系统应支持导入 `.srt`。
- `FR-051`：用户可以把候选词加入学习库，状态变为“待学习”。
- `FR-065`：词条只有满足跨日期规则才能变为“已掌握”。
- `FR-075`：AI 内容必须经用户确认后才能保存。

功能需求通常可以写成“当用户做 X 时，系统应做 Y”。

#### 3.2 非功能需求（Non-functional Requirement, NFR）

非功能需求描述系统**做得怎么样**：性能、隐私、安全、可靠性、可用性、兼容性、可维护性等质量属性。

SceneLingo 例子：

- `NFR-001`：导入 2,000 条 cue 的 SRT 不超过 3 秒。
- `NFR-005`：没有用户主动操作时，不产生千问请求。
- `NFR-006`：服务只监听 `127.0.0.1`，API Key 不进仓库和日志。
- `NFR-012`：P0 需求必须有自动化或可重复的验收。
- `NFR-019`：使用本地时区，日界线 00:00。

#### 3.3 两者不是“功能重要、非功能次要”

很多项目失败不是因为功能少，而是因为：

- 太慢（性能）；
- 数据丢了（可靠性）；
- 隐私泄露（安全）；
- 换个电脑跑不起来（兼容性）；
- 改一个功能牵一发而动全身（可维护性）。

SceneLingo 尤其如此：如果“隐私”做不好，用户不敢导入真实字幕；如果“持久化”做不好，复习记录丢失，整个学习闭环就失效。

#### 3.4 一个容易混淆的点

同一个目标可能同时产生 FR 和 NFR：

- NFR-005 说“不得自动上传字幕”；
- FR-024 说“发送前必须显示预览并让用户确认”。

前者是质量约束，后者是实现这个约束的用户可见行为。**NFR 往往需要 FR 来落地，FR 也受 NFR 约束。**

#### 3.5 非功能需求也必须可测试

“系统要安全”不是可测试的 NFR。可测试的写法是：

- 服务仅监听 `127.0.0.1`，局域网另一台设备无法访问；
- 仓库扫描找不到完整 API Key；
- 日志中不出现完整字幕或密钥；
- 无用户操作时网络监控无千问请求。

这就是为什么 SceneLingo 的 NFR 都带“验证方式”。

### 4. 用户需求与技术方案有什么区别

#### 4.1 定义

- **用户需求（User Requirement）**：用户要解决的问题、要获得的价值、不能接受的约束。
- **技术方案（Technical Solution / Design）**：实现用户需求的手段，例如框架、数据库、接口、算法。

#### 4.2 为什么必须区分

如果把技术方案当成需求，会带来三个问题：

1. **过早锁定**：还没理解问题，就选了工具，后面很难改。
2. **无法判断对错**：用户说“我要 SQLite”，你无法判断这个方案是否真的解决了他的问题。
3. **范围蔓延**：技术选型被当成功能，团队花时间争论工具，而不是验证价值。

#### 4.3 SceneLingo 的例子

| 用户需求（User Requirement） | 可能的技术方案（Technical Solution） | 为什么技术方案不是需求 |
| --- | --- | --- |
| 我想在没网时也能复习 | 用 SQLite 本地保存；前端缓存 | 用户要的是“离线可用”，不是“SQLite” |
| 我不想字幕被随便上传 | 本地 FastAPI 服务；调用前预览；只发送选中的 cue | 用户要的是“数据可控”，不是“FastAPI” |
| 我想知道单词是否真的记住 | 间隔复习算法；跨日期判定；复习历史 | 用户要的是“可信的掌握”，不是“SM-2 算法” |
| 我想在 Mac 上直接用 | macOS 本地应用；浏览器界面；本地 TTS | 平台是约束，不是功能本身 |
| 我想听到单词发音 | macOS `say`；本地 TTS；后续 Piper | 用户要的是“能听”，不是“某个语音引擎” |

#### 4.4 技术约束可以写进 SRS，但要标明身份

SceneLingo 的立项报告已经确认了一些技术约束：

- macOS；
- HTML/CSS/JavaScript；
- Python/FastAPI；
- SQLite；
- 千问 API；
- pytest；
- Git。

这些可以写进 SRS 的“约束”或“参考”，但不应被描述成“用户需求”。例如：

- 错误写法：“用户需要 SQLite。”
- 正确写法：“数据应本地持久化；立项已确认使用 SQLite 作为存储技术（技术约束）。”

同样，“用 SM-2 算法”不是需求；“词条必须跨日期复习后才能判定掌握”才是需求。算法是实现细节，可以在架构阶段选择。

#### 4.5 为什么 SRS 里还保留技术选型

因为项目已经有用户确认的技术约束，完全忽略它们也不现实。正确做法是：

- 把技术选型放在“约束/参考”位置；
- 不用技术选型替代用户价值；
- 如果技术选型与需求冲突，优先讨论需求，而不是强行让需求适配工具。

### 5. 什么是 MVP（Minimum Viable Product）

#### 5.1 定义

**MVP（Minimum Viable Product，最小可行产品）** 是用最小范围完成核心价值闭环、能够真实使用并验证关键假设的版本。

三个关键词：

- **Minimum（最小）**：不是功能越多越好；
- **Viable（可行）**：能真实解决一个问题，不是只能演示；
- **Product（产品）**：有人真的会用，而不是一段技术 Demo。

#### 5.2 MVP 不是“半成品”或“演示版”

- 演示版（Demo）：能展示一个亮点，但不保证数据、异常、持久化。
- 原型（Prototype）：用来验证界面或交互，可能没有真实后端。
- MVP：能完成端到端任务，数据能保存，异常有处理，用户可以持续使用。

SceneLingo 的 MVP 不是“能导入一份字幕”就结束，而是：

```text
导入字幕 → 浏览语境 → 按需翻译/解释 → 加词 → 朗读
→ AI 辅助（可选） → 复习 → 保存记录 → 下次继续
```

这个闭环缺任何一环，都不能算“可用于英语学习”。

#### 5.3 如何划 MVP 边界

SceneLingo 用了三层：

| 层级 | 含义 | 例子 |
| --- | --- | --- |
| P0 | MVP 必须 | SRT/VTT 导入、单句翻译、加词、拼写/词义回忆、跨日期掌握 |
| P1 | MVP 可选/后续优先 | 语境解释、英文表达练习、自由问答、短语比较、备份 |
| P2/OUT | 当前不做 | 多用户、云同步、视频播放、发音评分、自动批量翻译 |

划分依据不是“难不难”，而是：

1. 是否核心学习闭环必需？
2. 是否有已确认的需求来源？
3. 是否能独立验收？
4. 是否会显著增加隐私、成本或复杂度？

#### 5.4 MVP 与“先完成再完善”的关系

立项报告说“先完成再完善”。这不等于“先随便做，以后再补需求”。MVP 的正确做法是：

- 先完成**核心闭环**；
- 明确哪些是 P0，哪些是 P1；
- P1 不是“以后一定做”，而是“需要时再批准”；
- 不把未确认的 README 功能自动塞进 MVP。

### 6. 为什么不能跳过需求分析直接编程

#### 6.1 变更成本随阶段上升

软件工程里一个常见规律：**越晚发现错误，修复成本越高。**

- 需求阶段发现“掌握规则没定义”：改一段文档。
- 编码阶段发现：改状态机、数据库、测试、界面。
- 上线后发现：已有学习记录可能全部不可信，甚至要迁移数据。

#### 6.2 SceneLingo 的具体风险

**例子 1：“掌握”没有定义**

如果直接编程，可能会出现：

- 今天答对 3 次 → 标记“已掌握”；
- 明天全忘 → 用户不再复习；
- 学习效果被高估。

这正是立项报告明确禁止的。SRS 因此把“掌握”写成可测试规则：3 个不同日期、至少一次距首次成功 ≥7 天、最近一次成功。没有这条规则，测试人员无法判断“掌握”是否实现正确。

**例子 2：“AI 聊天”没有数据边界**

如果直接编程，可能会：

- 导入字幕后自动把整部字幕发给千问；
- 为了“上下文更完整”，把整个学习库也发过去；
- 把 API Key 写进前端。

这些都可能违反“本地优先、未经授权不得上传”的项目原则。SRS 因此在第 10 节定义发送矩阵和预览确认。

**例子 3：“支持 VTT”没有异常规则**

真实字幕可能有：

- BOM；
- 非 UTF-8 编码；
- `NOTE` 块；
- 重叠时间轴；
- 格式标签；
- 空 cue。

如果需求只写“支持 VTT”，实现者可能只处理最标准的一种，测试也无法判断“支持”到底意味着什么。

#### 6.3 需求分析不是“瀑布”

有人会误解：需求分析就是“一开始把所有事情定死，然后不许改”。不是。

更合理的理解是：

- 先建立**足够好的基线**，让设计和实现有依据；
- 用迭代和变更控制处理新信息；
- 不把“没想清楚”伪装成“敏捷”；
- 不把“以后再说”当成需求。

SceneLingo 的做法是：

- P1 建立 SRS 基线；
- 未决问题用 `OI-xx` 明确记录；
- 变更写入 `docs/06`；
- 每个阶段同时做工程验收和认知验收。

### 7. 什么是验收标准（Acceptance Criteria）与需求追踪（Requirements Traceability）

#### 7.1 验收标准

**验收标准（Acceptance Criteria, AC）** 是判断一个需求是否被满足的可观察条件。好的 AC 通常具备：

- 具体（Specific）；
- 可测量（Measurable）；
- 可复现（Reproducible）；
- 可判定（Testable）；
- 与需求直接相关。

常见写法是 **Given–When–Then（给定–当–则）**：

> 给定一个学习库中有 3 个词条的用户；
> 当用户同一天对同一个词答对 3 次；
> 则词条状态仍为“学习中”，不能变为“已掌握”。

SceneLingo 的 AC 例子：

- `AC-FR-020-1`：选中一条 cue 请求翻译，发送预览只包含该 cue 的文本。
- `AC-FR-065-1`：同一天答对 3 次，词条仍为“学习中”。
- `AC-FR-073-1`：启动、导入、浏览、复习期间无千问 API 请求。

#### 7.2 验收标准不是什么

- 不是“系统运行正常”；
- 不是“用户体验良好”；
- 不是“代码写完了”；
- 不是“测试通过了”但没有说明测了什么；
- 不是“我觉得可以了”。

#### 7.3 验证与确认（Verification vs Validation）

这两个词经常混淆：

- **Verification（验证）**：我们是否正确地构建了系统？即是否符合 SRS、设计、规范。
- **Validation（确认）**：我们是否构建了正确的系统？即是否真的解决用户问题。

SceneLingo 的例子：

- Verification：FR-065 的跨日期规则是否按 AC 通过。
- Validation：这个“掌握”规则是否真的帮助用户记住单词，而不是让用户觉得繁琐。

两者都需要，不能只用测试通过代替学习效果。

#### 7.4 需求追踪

**需求追踪（Requirements Traceability）** 是建立需求与其他 artifacts 之间的可追踪关系：

```text
用户目标
  → 用户需求
    → 功能需求 FR-xxx
      → 业务规则 BR-xxx
        → 验收条件 AC-FR-xxx-n
          → 验收场景 AT-xxx
            → 测试用例 / 手工验收
              → 缺陷 / 变更
```

SceneLingo 的例子：

```text
“掌握不能靠同日三次”
  → FR-065 掌握状态判定
    → BR-REV-05 跨日期规则
      → AC-FR-065-1/2/3
        → AT-009 跨日期掌握与回退
          → 测试用例（可控日期）
```

#### 7.5 为什么需要追踪

1. **覆盖检查**：有没有需求没有测试？有没有测试没有需求？
2. **变更影响分析**：修改掌握规则，会影响哪些 AC、测试、数据？
3. **验收透明**：用户能看到“这条需求对应哪个测试”。
4. **防止范围蔓延**：新增需求必须进入矩阵，而不是悄悄写进代码。
5. **防止“测试通过但需求没做”**：测试和需求有明确映射。

#### 7.6 需求变更时会发生什么

假设用户决定把拼写判定从“连字符必须保留”改成“连字符和空格等价”：

需要同步修改：

- `BR-REV-03` 拼写判定规则；
- `AC-FR-061-2` 验收条件；
- `AT-008` 测试步骤；
- 测试用例和测试数据；
- 可能还有用户提示和帮助文档；
- 变更记录 `docs/06`。

这就是追踪矩阵的价值：它让“改一条规则”的影响可见，而不是靠记忆。

### 8. SceneLingo 的需求工程流程

本项目 P1 的实际流程可以概括为：

```text
阅读立项报告和 README
  → 识别用户、场景、目标
  → 区分用户需求 / 业务规则 / 技术建议
  → 编写 FR（功能）和 NFR（质量）
  → 为模糊点编写业务规则
  → 枚举异常场景
  → 定义云端数据边界
  → 为每条核心需求写 AC
  → 建立 FR → AC → AT 追踪
  → 记录未决问题 OI 和假设 AS
  → 用户确认，形成需求基线
```

其中几个关键动作：

1. **不修改已确认的立项报告**：发现差异，写到 SRS 的“差异”和 `OI` 中。
2. **不把 README 里的候选功能自动升级为 P0**：来源标记 `U-RM` 与 `U-00` 区分。
3. **不把技术方案写成需求**：FastAPI、SQLite 只作为约束/参考。
4. **不把“建议”伪装成“已确认”**：掌握规则、统计口径、文件限制都标“建议，待确认”。
5. **不跳过异常和数据边界**：这两部分往往比正常流程更能暴露风险。

### 9. 常见误区

| 误区 | 表现 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 把技术方案当需求 | “系统应使用 SQLite” | 过早锁定，无法判断价值 | 先写“数据本地持久化”，技术选型单列 |
| 用形容词代替 AC | “界面要友好”“速度要快” | 无法验收 | 写可测指标和具体行为 |
| 只写正常流程 | 只写“导入成功” | 异常时数据损坏或用户卡死 | 写无效文件、重复导入、断网、超时 |
| 功能清单当场景 | “支持翻译、支持朗读、支持 AI” | 不知道用户怎么用，功能之间不闭环 | 写端到端流程和用户故事 |
| 需求没有编号 | 变更时找不到影响范围 | 测试遗漏、范围蔓延 | FR/NFR/AC/AT 编号 |
| 把 AI 生成内容当事实 | 不确认就保存 | 错误内容进入学习库 | 用户确认 + AI 标识 + 不自动改状态 |
| 忽略数据边界 | 自动上传整部字幕 | 隐私风险、成本失控 | 发送矩阵 + 预览 + 最小化 |
| 把“以后再说”当需求 | 未决问题不记录 | 实现时临时拍脑袋 | 用 OI 记录，明确决策时点 |
| 用测试通过代替学习效果 | 功能都通过就算成功 | 软件完成但英语没进步 | P7 独立基线/复测 |
| 需求文档写完就锁死 | 不允许变更 | 与真实使用脱节 | 基线 + 变更控制 + 迭代 |

## P2：系统架构（Software Architecture）

> 本阶段的需求基线是 `docs/01-需求规格说明.md` V0.2，架构基线是 `docs/02-系统架构设计.md` V0.1。下面每个概念都对应 SceneLingo 的真实位置和例子；架构基线仍需用户审核。

### 0. 架构阶段在做什么

需求阶段回答“做什么”，架构阶段回答“系统由哪些部分组成、它们如何协作、边界在哪里”。

架构不是：

- 数据库表设计；
- 完整 API 字段契约；
- 界面视觉稿；
- 把技术名词堆在一起。

架构是：

- 对系统边界的决定；
- 对模块职责和依赖方向的决定；
- 对关键数据流和失败处理的决定；
- 对技术选型和取舍的记录；
- 对“现在不做什么”的明确说明。

SceneLingo 的架构结论是一个**简单模块化单体**：一个 FastAPI 进程、一个 SQLite 数据文件、原生前端、一个千问网关。这个结论本身就是架构决策，而不是代码细节。

---

### 1. 软件架构（Software Architecture）

#### 定义

软件架构是系统的**结构性决策集合**：系统由哪些组件组成，组件各自负责什么，它们如何连接，哪些依赖允许存在，数据和控制如何流动，以及哪些质量属性（隐私、可维护性、性能、成本）通过什么方式保证。

一个好的架构不仅说明“有什么”，还说明“为什么这样、什么不在范围、什么风险被接受”。

#### 在 SceneLingo 中的位置

- `docs/02-系统架构设计.md` 第 2 节：总体架构与部署拓扑。
- 第 3 节：前端、后端、数据库、AI 服务职责。
- 第 4 节：模块划分与依赖规则。
- 第 11 节：技术选型和替代方案。
- 第 13 节：架构验收清单。

#### 具体例子

SceneLingo 没有采用微服务，而是选择“单进程 + 模块化单体”：

- 一个 FastAPI 进程同时提供静态页面和 `/api/v1`。
- 一个 SQLite 文件保存本地学习数据。
- 千问只通过 `QwenGateway` 访问。

这不是因为微服务“不好”，而是因为本项目是单用户、单机、个人学习应用。拆成多个服务会引入网络调用、服务发现、分布式事务、部署和调试成本，却换不来这个规模所需的好处。架构文档同时写明：模块边界保留，将来真需要时再拆。

**判断标准**：如果一条“架构决定”不能用“它保护了什么质量属性、付出了什么代价”来解释，它很可能只是技术偏好。

---

### 2. 前端（Frontend）

#### 定义

前端是运行在用户设备（这里是浏览器）中的界面层，负责呈现信息、接收用户操作、维护界面状态，并通过 API 与后端通信。

前端不等于“只画页面”。它要处理加载状态、错误状态、表单校验、可访问性、交互反馈和数据展示的一致性；但它不应成为业务事实的最终裁决者。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §3.1。
- 计划目录：`app/web/`，例如 `api-client.js`、`subtitle-view.js`、`review-view.js`、`chat-view.js`、`state.js`。
- 技术选择：原生 HTML/CSS/JavaScript ES Modules，不引入 React/Vue、不引入 Node 构建链。

#### 具体例子

AI 聊天发送前，前端 `chat-view.js` 负责：

1. 收集用户输入和选中的 cue/词条；
2. 调用 `POST /api/v1/ai/send-plans` 生成发送计划；
3. 展示完整预览：消息、附件、历史条数、目标模型、目的地“千问 API”、预估费用；
4. 用户确认后，才调用 `/execute`；
5. 用 SSE 接收增量文本，显示“生成中”，最终按 `done`/`error` 更新状态。

前端**不**做这些事：

- 不自己拼一个“差不多”的请求直接发给千问；
- 不计算复习的下次日期；
- 不把 API Key 存进 `localStorage`；
- 不用 `innerHTML` 渲染字幕或 AI 文本。

**具体风险例子**：如果把字幕文本直接塞进 `innerHTML`，恶意字幕里的 `<script>` 或事件属性就可能执行。架构因此要求不可信内容只用文本节点或安全渲染函数。

---

### 3. 后端（Backend）

#### 定义

后端是运行在服务器/本机进程中的应用层，负责接收请求、执行业务用例、协调数据持久化和外部服务、返回结果。它通常也是权限、事务、错误处理和敏感配置的集中点。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §3.2。
- 计划目录：`app/api/`（HTTP 适配）、`app/services/`（用例与事务）、`app/domain/`（规则）、`app/repositories/`（持久化）、`app/integrations/`（外部适配器）。
- 关键端口：`QwenGateway`、`IpaDictionary`、`TtsGateway`、`SecretStore`、`Clock`。

#### 具体例子

复习提交走后端 `ReviewService`：

- 校验词条是否存在、评分是否合法；
- 读取当前间隔和历史成功日期；
- 按 `BR-REV-04` 计算下次日期；
- 按 `BR-REV-05` 判断是否满足掌握；
- 在一个事务中写入本次尝试并更新词条状态；
- 用客户端 `attempt_id` 保证刷新/重试不重复计分。

如果把“下次日期”和“是否掌握”放在前端计算，用户刷新、换浏览器或改本地时间就可能产生不一致；后端也无法阻止重复提交。因此，前端可以显示结果，但不能成为规则的事实来源。

**边界例子**：`ReviewService` 不直接发 HTTP 到千问，也不直接拼 SQL；它依赖注入的端口，由仓储和适配器实现细节。

---

### 4. 数据库（Database）

#### 定义

数据库是持久化数据的系统，负责在进程重启后仍保存数据，并通过事务、约束和查询保证数据的一致性与可访问性。数据库设计包括数据模型、表结构、索引、约束和迁移；架构阶段只确定“数据库的职责和边界”，不展开表设计。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §3.3。
- 计划目录：`app/repositories/`；SQLite 文件位于本机应用数据目录。
- 后续独立文档：`docs/03-数据库设计.md`（本阶段不做）。
- 关键概念：事务、唯一约束、外键、WAL、迁移版本、冻结语境快照。

#### 具体例子

导入字幕后写入字幕、cue 和统计，必须在一个事务中完成：

```text
BEGIN IMMEDIATE
  → 写入字幕记录
  → 写入所有有效 cue
  → 写入统计结果
COMMIT
```

如果写到一半磁盘满或约束失败，就回滚，不能留下“字幕存在但 cue 不全”的半份数据。复习提交也类似：一次尝试和词条状态更新必须一起成功，避免“历史记了但状态没变”。

另一个例子是字幕删除：有词条/复习历史关联时，数据库不能靠 `ON DELETE CASCADE` 静默删掉学习记录。架构要求要么保留冻结语境快照，要么阻止硬删除；这既是一条需求，也是一条数据完整性约束。

**注意**：本节讲的是数据库的**职责**。具体有哪些表、字段、索引和外键，属于 `docs/03`，不能在架构阶段假装已经决定。

---

### 5. API（Application Programming Interface）

#### 定义

API 是模块或系统之间约定的调用接口：谁可以调用、传什么、返回什么、出错时怎样表示。它既是技术契约，也是边界：调用方不需要知道内部实现，但不能绕过约定直接访问内部数据。

API 不只指“HTTP 接口”。项目内部的 `QwenGateway`、`ReviewRepository` 也是接口。架构要同时设计外部 API 和内部端口。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §7（接口设计原则）、§5.2（发送计划流程）。
- 外部 API：`/api/v1/*`，JSON + SSE，同源访问。
- 内部端口：`SubtitleRepository`、`VocabularyRepository`、`ReviewRepository`、`QwenGateway`、`TtsGateway`、`SecretStore`、`Clock`。
- 完整 API 契约：后续独立阶段，不在本文件定稿。

#### 具体例子

AI 发送采用两阶段接口：

1. `POST /api/v1/ai/send-plans`：后端根据用户选择的附件和历史开关，生成**不可变发送计划**，返回完整预览。
2. `POST /api/v1/ai/send-plans/{id}/execute`：用户确认后，后端只执行这个计划。

为什么不在前端拼好正文直接 POST 给 `/chat`？

- 预览和实际发送可能不一致：用户看到 A，代码却发了 A+B；
- 后端无法证明“用户确认过这段内容”；
- 重复点击可能重复计费；
- 后端难以统一做历史开关、模型选择和费用记录。

两阶段设计把“确认的内容”变成服务端可验证的对象，并用一次性计划和 `request_id` 解决重复执行。代价是计划存储、过期和清理的复杂度；这是有意识的取舍。

内部接口也一样：`QwenGateway` 的契约规定“支持流式、取消、用量、分类错误”，测试可以换成假网关，不需要真的联网。

---

### 6. 模块化（Modularity）

#### 定义

模块化是把系统拆成职责相对独立、边界清晰、可以分别理解和修改的单元。好的模块化追求**高内聚、低耦合**：相关规则放在一起，模块之间通过稳定接口协作，而不是互相读对方的内部数据。

模块化不等于“文件多”或“目录深”。如果两个模块仍然共享全局变量、直接访问对方的表，或者改一个功能要同时改五处，那只是物理拆分，不是逻辑模块化。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §4.1 模块表、§4.2 依赖规则、§4.3 建议目录。
- 依赖方向：`api → services → domain`；`repositories` 和 `integrations` 实现端口。
- 规则：domain 不导入 FastAPI/sqlite3/httpx；路由不直接写 SQL；AI 模块不直接操作词汇表。

#### 具体例子

“加词”这件事涉及字幕、词形、词条、语境和复习状态，但架构没有让 AI 聊天模块直接改词汇表：

```text
AI 聊天服务
  → 调用 VocabularyService.add_word(...)
      → 校验去重键
      → 创建/复用词条
      → 追加语境快照
      → 返回结果
```

这样：

- 加词规则只有一处；
- AI 聊天不需要知道词汇表结构；
- 测试词汇规则时不需要启动 AI；
- 将来改去重规则，不会漏改聊天模块。

另一个例子是 `QwenGateway`：如果以后换模型供应商，只改适配器，服务层和前端不受影响。这是模块化带来的“可替换性”。

**反例**：如果 `chat.py` 里直接 `import sqlite3` 并执行 `INSERT INTO vocabulary`，短期能跑，但词汇规则会分裂成两份，测试和修改都会变难。

---

### 7. 数据流（Data Flow）

#### 定义

数据流描述数据从输入到输出经过哪些组件、在每一步发生什么转换、在哪里被持久化、在哪里离开本地边界。它帮助我们发现隐藏的耦合、重复写入、隐私泄露和失败时的半成品。

数据流图不是流程图：流程图强调“用户点哪个按钮”，数据流强调“数据变成什么、去了哪里”。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §5.1（字幕导入到词汇保存）、§5.2（用户提问到千问回答）、§6（本地/云端边界）。
- 需求位置：`docs/01` 第 4 节流程、第 10 节发送矩阵。

#### 具体例子：字幕导入到加词

```text
用户选择 SRT
→ 前端上传文件
→ API 校验扩展名/大小/编码
→ 解析器生成 cue
→ 清洗文本
→ 词形统计（BR-SUB-08）
→ 事务写入字幕/cue/统计
→ 前端显示字幕和候选词
→ 用户点击“加入学习库”
→ VocabularyService 查重
→ 创建词条 + 冻结语境快照
→ 事务提交
```

这条流里，数据从未离开本机；统计发生在写入前；加词发生在用户点击后。每一段都有明确的输入输出和失败处理。若在“写入字幕”处失败，前面的解析结果丢弃，不产生半份数据。

#### 具体例子：用户提问到千问回答

```text
用户输入问题 + 选择附件
→ 后端生成不可变发送计划
→ 前端展示完整预览
→ 用户确认
→ 后端复核云端开关/Key/模型
→ 只发送计划中的内容到千问
→ 流式返回增量
→ 用户看到回答
→ 后端记录会话、执行状态、费用
→ 用户另一次确认后才保存到学习库
```

关键不是“调用了 API”，而是数据边界：默认不带历史；预览等于实际发送；费用记录只留本地；AI 回答不自动变成学习事实。

**数据流分析要问的问题**：

- 数据在哪一步改变？谁有权改变？
- 哪一步可能失败？失败了留下什么？
- 哪一步离开本地？离开的到底是哪几个字段？
- 哪一步可能重复？重复会造成什么？

### 8. 技术债（Technical Debt）

#### 定义

技术债是为了短期交付或学习目标，**有意识地**接受某种设计不完整，从而在未来付出额外维护成本。它像债务：现在借了速度，将来要还利息。技术债不必然是错误；危险的是“没有记录的债”和“永远不还的债”。

技术债分两类：

- **有意债务**：明确知道代价、记录了原因和偿还条件；
- **无意债务**：不知道有问题，或知道但假装没有，通常来自赶工、缺少测试、复制粘贴。

#### 在 SceneLingo 中的位置

- 架构位置：`docs/02` §11.3 架构风险、§14 后置设计事项。
- 需求位置：`docs/01` 第 12 节风险、P1 保留项。
- 变更记录：`docs/06-项目变更记录.md`（后续使用）。

#### 具体例子

SceneLingo 当前有意接受的技术债：

| 技术债 | 为什么现在接受 | 利息/风险 | 偿还触发条件 |
| --- | --- | --- | --- |
| 原生 JS 管理界面状态 | 避免 Node/React 构建链，先把学习闭环做出来 | 页面变多后状态可能分散、重复请求 | 出现跨页面状态不同步或重复请求难以定位时，引入轻量状态模块/框架并补测试 |
| 手写 SQL + 手写迁移 | 学习 SQL、减少 ORM 魔法、依赖少 | 迁移易错、重复 SQL、注入风险 | 仓储重复明显或迁移出错影响数据时，引入查询构建/迁移工具 |
| macOS 专属 TTS 子进程 | 保证本地语音、可审计 | 子进程清理、临时文件、跨平台不可用 | 支持 Windows/Linux 或 TTS 故障率上升时，抽象为多平台适配器 |
| 费用为估算而非账单 | API 用量字段和价格表未完全验证 | 用户可能误以为精确；价格变化导致偏差 | 供应商提供稳定 usage/价格 API 时，改为精确计算并保留版本 |
| 单用户、无认证 | 目标就是个人本机应用 | 不能多人/远程使用；本机恶意进程不受防 | 出现多用户/远程访问需求时，重新设计认证与隔离 |
| 备份/恢复为 P1 | 先保证核心闭环 | 本地磁盘损坏可能丢数据 | 正式长期使用前，至少提供手动备份或明确数据位置 |
| API 契约后置 | 先定架构边界，避免过早锁字段 | 前后端联调可能返工 | 进入实现前必须补端点/字段/错误码契约 |

**判断例子**：“原生 JS 状态分散”是有意债务，因为架构明确写了代价和偿还触发条件；“没有测试复习跨日期规则”如果发生了，就是无意债务，因为它直接破坏核心验收，而且没有记录。

技术债的管理不是“全部消灭”，而是：

1. 记录它；
2. 说明为什么借；
3. 估算利息；
4. 设定偿还触发条件；
5. 不让它悄悄变成“永久架构”。

## P3：数据库设计与任务拆分（Database Design & Task Breakdown）

### 0. 这一阶段在做什么

P2 回答了“系统分成哪些模块、谁依赖谁”，但没有回答“数据具体怎么放”。P3 做两件事：

1. **把数据定下来**：有哪些实体、彼此什么关系、受什么约束、删除时保留什么——`docs/03`。
2. **把工作切开**：把架构的 11 步实现顺序变成 13 张可独立验收的任务卡——`tasks/`。

这一阶段仍然**不写建表 SQL、不写应用代码**。它产出的是“实现前的契约”。

---

### 1. 什么是数据库（Database）

**定义**：数据库是按某种结构组织、可长期保存、可被多个操作安全读写的持久化数据集合；数据库管理系统（DBMS，Database Management System）负责存储、并发控制、事务和查询。SceneLingo 用的是**嵌入式关系数据库**（Embedded Relational Database）SQLite：没有独立服务器进程，数据就是数据目录里的一个文件。

**在 SceneLingo 中的位置**：
- 架构：`docs/02` §3.3 规定数据库只由后端仓储访问，前端不碰。
- 设计：`docs/03` 定义 14 张逻辑表。
- 文件：`~/Library/Application Support/SceneLingo/scenelingo.db`。

**具体例子**：你导入一部字幕，系统把字幕、每条 cue、每个词形的出现次数写进数据库；关掉应用再打开，这些数据还在——这不是“界面记住了”，而是磁盘上的文件没丢。反过来说，如果只把数据放在前端内存里，刷新页面就没了，那是“状态”不是“数据库”。

**为什么不用现成的云数据库**：单用户、单机、离线优先，引入服务器只会增加部署和隐私成本；SQLite 支持事务、外键和 WAL，足够这个规模。

---

### 2. 为什么需要主键和外键（Primary Key & Foreign Key）

**定义**：
- **主键（Primary Key）**：表中能唯一标识一行的列或列组合；不可重复、不可为空。
- **外键（Foreign Key）**：一列的值必须来自另一张表的主键（或唯一键），用来表达“这两行有关系”，并由数据库强制检查。
- **唯一约束（Unique Constraint）**：某列/组合不允许重复，但不一定是主键。

**在 SceneLingo 中的位置**：`docs/03` §10。

**具体例子**：

1. **主键**：`cue.id` 唯一标识一条句子。若两条 cue 共用一个 ID，“点击来源语境跳转”就会跳到随机一条。
2. **外键**：`context_ref.cue_id` 必须指向真实存在的 `cue.id`。如果词条语境指向一条被删掉的 cue，而数据库不检查，界面就会出现“点开空白”的悬空引用。
3. **唯一约束**：`learning_item` 的 `(entry_type, dedupe_key)` 唯一，保证 `don't` 不会因为大小写或弯撇号不同被创建两次；`review_attempt.attempt_token` 唯一，保证刷新页面不会把同一次作答算两次。

**关键区别**：主键回答“这一行是谁”，外键回答“这一行和谁有关”，唯一约束回答“什么情况下不允许再出现一份”。三者不能互相替代：ID 唯一不代表业务不重复（两条不同 ID 的词条可以都叫 `don't`），外键有效也不代表语义正确。

---

### 3. 什么是实体关系图（Entity-Relationship Diagram, ERD）

**定义**：ER 图用图形表达**实体**（Entity，一类需要保存的对象）、**属性**（Attribute，实体的字段）和**关系**（Relationship，实体之间的数量对应），并标注基数（Cardinality，如 1:1、1:N、N:M）。它是设计和沟通工具，不是数据库本身。

**在 SceneLingo 中的位置**：`docs/03` §4.2 的 Mermaid `erDiagram`。

**具体例子**：

```text
subtitle 1 ──── N cue           一部字幕包含多条句子
learning_item 1 ──── N review_attempt   一个词条有多次复习
learning_item 1 ──── 0..1 review_state  一个词条只有一个当前状态
```

读图时先看两端符号：`||--o{` 表示“左边恰好一个，右边零个或多个”。所以“一部字幕对应零到多条 cue”是合法的（刚创建还没解析完时可以是零），而“一条 cue 必须属于恰好一部字幕”也是强制的。

**为什么要画**：文字描述“词条有语境、语境来自 cue、cue 属于字幕”很容易漏掉一句“删字幕时语境怎么办”。ER 图逼你把每条连线想清楚，Mermaid 还能直接进 Git 评审。

---

### 4. 什么是数据库迁移（Database Migration）

**定义**：迁移是**对数据库结构或数据的有序、可重复、可追踪的变更**，通常表现为一组带版本号的脚本：每个脚本把数据库从版本 N 变到 N+1。迁移解决的是“我已经有数据了，代码升级后表结构变了怎么办”。

**在 SceneLingo 中的位置**：架构 §3.3/§11.1、`docs/03` §11、任务卡 `TASK-002`。

**具体例子**：假设第一版 `learning_item` 没有 `ipa` 字段，第二版要加。迁移做的是“加一列”，而不是“删库重建”——因为删库会丢掉用户所有词条和复习历史。SceneLingo 的做法：

- 用 `PRAGMA user_version` 记录当前版本；
- 启动时比对版本，低于代码版本就按顺序执行；
- **执行前自动备份**，失败就停止启动，保留原库；
- 迁移只向前，不改已发布的脚本。

**反例（必须避免）**：检测到表结构不对就 `DROP TABLE` 重建、迁移失败后“再试一次”并继续提供服务、用 ORM 自动建表替代迁移。这三种做法都会在用户真实数据上造成不可恢复的损失。

---

### 5. 什么是 API 健康检查（Health Check）

**定义**：健康检查是一个轻量接口，用来回答“服务现在是否活着、能不能接受请求”。它通常返回状态码和极少量信息，不查业务数据、不暴露内部细节。

**在 SceneLingo 中的位置**：`GET /api/v1/health`，见架构 §7.3 与 `TASK-001`。

**具体例子**：

```json
{"status": "ok", "version": "0.1.0", "time": "2026-10-29T08:00:00Z"}
```

反面例子是“健康检查里顺手返回数据库路径、当前用户、配置、依赖版本”——这些信息对判断存活没有帮助，却把内部结构暴露给任何能访问端口的程序。SceneLingo 的原则是：健康检查**只证明进程活着**；需要更多信息时用受令牌保护的系统接口。

**为什么重要**：本地应用也需要它。启动脚本要确认服务起来了、测试要确认没有半启动状态、用户排查“打不开”时第一件事就是看健康检查。没有它，所有问题都变成“页面白屏”。

---

### 6. 业务逻辑与数据存储有什么区别（Business Logic vs Data Storage）

**定义**：
- **业务逻辑**：系统“应该怎么判断、怎么计算”的规则，例如“什么算一次成功”“间隔如何推进”“删除字幕时保留什么”。
- **数据存储**：系统“把什么记下来、怎么保证记对”的结构与约束，例如表、字段、主键、事务。

两者相关但不等价：同一套存储可以承载不同规则；同一套规则也可以换一种存储。**规则写在代码和文档里，约束写在数据库里，两者要互相校验。**

**在 SceneLingo 中的位置**：
- 业务逻辑：`docs/01` 第 6 章（BR-REV-04/05、BR-SUB-12）、`app/domain/`（计划）。
- 数据存储：`docs/03` 表结构与约束、`app/repositories/`（计划）。

**具体例子**：

| 规则 | 属于 | 谁保证 |
| --- | --- | --- |
| “同一天多次成功只算一天” | 业务逻辑 | 领域函数按本地日期去重 |
| “成功次数必须等于历史里 `is_success` 的条数” | 两者交界 | 事务 + 可重算的投影 + 测试 |
| “一条词条不能有两个相同去重键” | 数据存储 | 唯一约束 |
| “删除字幕不删复习历史” | 业务逻辑 + 结构 | 删除策略 + `RESTRICT` 外键 |

**最容易犯的错**：把规则只写在数据库里（例如用触发器实现掌握判定），导致规则不可读、不可测、迁移困难；或者把规则只写在界面上（前端算完直接显示“已掌握”），导致刷新、重放、并发时数据不一致。SceneLingo 的选择是：**规则在后端领域层，约束在数据库，界面只展示**。
