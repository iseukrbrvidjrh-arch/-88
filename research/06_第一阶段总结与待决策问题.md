# 第一阶段总结与待决策问题

## 1. 最重要的五项差异

1. **产品入口不同**：enjoy_player 从媒体播放和时间轴训练出发；SceneLingo 从字幕文本、词条和复习出发。
2. **训练广度不同**：A 声称 Listen、Echo、Dictation、发音评分等多模式；B 已确认的核心更集中在阅读、朗读、词义/拼写复习。
3. **数据模型取舍不同**：A 的 schema 覆盖媒体、录音、同步和多类训练；B 用较小的 SQLite 模型强调复习事实不可变、语境快照和单机可审计。
4. **平台和技术栈不同**：A 是 Flutter/Dart，多平台；B 是 Python/FastAPI/原生 JS，macOS 本地优先。不能直接合并。
5. **工程证据都有限制**：两边都有文档和测试材料，但本阶段没有运行任一项目；A 的 README 功能、B 的设计文档都不能自动等同于验收完成。

## 2. 最值得借鉴的五项功能/思想

1. **以媒体时间轴/字幕 cue 作为共同学习上下文**：让听、看、查词、复习围绕同一片段，而不是孤立页面。
2. **同一片段支持多种主动练习**：优先研究听写或跟读中的一个最小闭环，不直接复制全部模式。
3. **清晰区分普通媒体与 YouTube 等特殊来源**：A 的架构分流思想有助于控制边界。
4. **训练数据与上下文的长期持久化**：A 的媒体/训练实体范围值得参考，但应映射到 B 的可审计模型，不能照搬 schema。
5. **产品级恢复、生命周期和跨平台测试意识**：A 的测试目录覆盖启动、恢复、关闭和发布流程；B 可借鉴测试分类，而不是只增加功能。

## 3. SceneLingo 当前最重要的五个问题

1. **完成度口径不够统一**：设计文档规划范围明显超过可直接确认的运行功能，需建立“源码/测试/实机”状态矩阵。
2. **媒体输入能力不足**：目前核心是 SRT/VTT 文本，缺少与音频/视频播放和定位的闭环；是否补齐取决于产品定位决策。
3. **前端复杂度正在上升**：原生 JS 同时承载多个页面、AI 流式、复习、设置和布局状态，未来回归风险高。
4. **真实验证尚未完成**：测试文件很多，但本轮没有运行；AI 上游、TTS、打包、迁移升级、隐私边界和大数据性能仍需隔离环境验证。
5. **扩展能力尚未产品化**：导出/恢复、表达练习、发音评分、词条归档、多供应商等仍是部分/待决事项，不能在未定方向前擅改数据库。

## 4. 建议升级优先级

- **P0：证据和可靠性**：完成现有闭环的隔离验证、状态矩阵、迁移/备份演练和关键数据一致性检查。
- **P1：学习闭环体验**：优化字幕 cue—词条—语境—复习的连续流程，确保离线核心可用。
- **P2：选择一个输入输出实验**：听写或跟读二选一，设定学习效果指标和隐私/成本边界。
- **P3：媒体和上下文扩展**：在产品负责人确认后评估音视频播放、定位、录音或特殊来源。
- **P4：平台化能力**：仅在确有需求时评估多供应商、同步、多平台和更复杂的组件体系。

这些优先级是研究结论，不是本阶段执行计划。

## 5. 需要用户决策的问题

1. SceneLingo 2.0 首要定位：字幕学习工具，还是带播放器的媒体英语训练平台？
2. 是否接受本地音视频播放；支持哪些文件格式和是否需要 YouTube？
3. 第一项新增训练选择：听写、跟读、表达练习，还是先不新增而优化现有复习？
4. 核心学习能力是否必须完全离线；AI 翻译/发音评分是否允许出网？
5. 是否需要多设备同步、账号和云端数据；若不需要，是否明确保持单机？
6. 目标发布方式是否能承担 enjoy_player 的 AGPL-3.0 合规义务？
7. 是否批准下一阶段在隔离临时数据库中运行现有测试和真实应用验收？
