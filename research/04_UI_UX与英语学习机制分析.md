# UI/UX 与英语学习机制分析

## 1. 证据边界

SceneLingo 的页面和交互证据来自 `app/web/index.html`、`app/web/app.js`、`app/web/style.css` 及 browser 测试脚本；业务证据来自 `app/api`、`app/services` 和 `app/domain`。enjoy_player 的 UI 只能从 Flutter 入口、架构文档、README、feature/测试材料静态判断；本报告不声称亲自操作过任一应用。

## 2. 信息架构比较

### enjoy_player

A 围绕媒体对象组织产品：媒体/视频 → 时间轴字幕/转录 → Listen、Echo、Dictation 等训练 → 词汇/复习。普通 URL/本地媒体与 YouTube 分开处理（`docs/architecture.md`），这是一项合理的边界设计：不同来源的播放、登录、字幕和限制不被强行伪装成同一种能力。Flutter feature-first、Riverpod 适合承载多页面状态，但用户需要理解媒体、训练模式、词汇和同步之间的层级。

### SceneLingo

B 以字幕库和学习库为主要入口：导入字幕 → 浏览 cue → 查询/翻译/朗读 → 加入词条 → 复习/记录；AI 聊天是独立辅助入口。`index.html`/`app.js` 将多个区块整合在单页原生 Web 界面中，优点是启动快、离线可用、流程直接；缺点是随着聊天、流式状态、设置、复习和布局偏好增加，单一前端状态容易互相影响。当前工作树中的前端改动未被本研究修改，且不将其内容作为稳定基线结论。

## 3. 关键交互流程审视

| 流程 | 体验价值 | 主要风险 | 建议观察点 |
|---|---|---|---|
| 导入字幕 | 快速把个人材料变成学习对象；B 还展示有效/无效统计 | 大文件、重复导入、解析警告可能打断用户 | A 是否支持多来源；B 是否始终分页/保持响应 |
| 选 cue 查词 | 把词义和真实语境绑定，优于孤立词表 | 候选词太多会造成选择负担 | 默认排序、已加入状态、语境展示是否清晰 |
| 朗读 | 提供输入后即时听觉反馈 | TTS 不等于真实发音训练；macOS 依赖 | 是否显示来源/失败可操作提示 |
| 复习 | 提供主动回忆和间隔机制 | 若只重复同日答题，容易产生虚假掌握 | B 的跨日期规则是重要保护；界面应说明原因 |
| AI 发送 | B 的预览让用户知道发送内容和费用，降低隐私惊讶 | 预览与执行、流式取消、失败状态需一致 | `ai_send_plan.py`、`api/ai.py` 的状态展示 |
| 媒体跟读/听写 | A 声称的输入输出循环更接近真实听说 | 录音/评分可能增加焦虑、成本和平台风险 | 先做小规模学习实验，不先做复杂评分 |

## 4. 第二语言习得视角

1. **可理解输入**：字幕提供真实语境，但“看懂中文翻译”不能替代听辨；A 的媒体播放与片段训练方向更接近输入循环。B 当前主要强项是语境词汇和可重复复习。
2. **主动回忆**：B 的 spelling/meaning review、`review_attempt` 与 `review_state` 支持主动提取，不应退化为只浏览词条。
3. **间隔与跨日期**：B 明确要求不同日期和至少间隔，避免单日重复造成掌握假象；这是学习机制和数据机制的共同优点。
4. **语境多样性**：`context_ref` 保留多个 cue 和冻结快照，有助于形成词义网络；应避免把 AI 解释直接当作事实而不经用户确认。
5. **输出练习**：表达重组、跟读、听写、纠错有潜在价值，但目前 B 的完整实现证据不足；A 的 README 声称不能替代对实际反馈质量的测量。
6. **认知负荷**：功能越多不一定越有效。应先让用户在一个片段完成“听—理解—回忆—复习”闭环，再提供高级 AI/评分/同步入口。

## 5. UI/UX 结论

- **值得借鉴**：A 的媒体对象—片段—训练模式结构；同一上下文贯穿不同练习。
- **B 应保留**：本地优先、当前 cue 作用域、AI 发送预览、来源标签、可恢复进度和明确失败状态。
- **需要产品验证而非立即改造**：是否加入视频播放器、跟读、听写、录音评分；这些都改变产品定位和数据模型。
- **成功指标**：不应只看页面数量，应观察用户完成一个学习片段所需时间、主动回忆比例、跨日期复习完成率、听辨/表达是否改善，以及 AI 调用是否真正增加学习量。
