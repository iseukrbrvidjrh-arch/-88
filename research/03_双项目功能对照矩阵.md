# 双项目功能对照矩阵

> A = `enjoy_player`；B = SceneLingo。结论按静态证据分级，未把文档声称当作实机验收。

| 功能模块 | A：enjoy_player | B：SceneLingo | 差异分析 | 初步建议 |
|---|---|---|---|---|
| 媒体输入 | Flutter 多平台播放器、本地/URL、YouTube 分流；`lib/main.dart`、`docs/architecture.md` | 主要处理 SRT/VTT，不负责视频播放器；`app/domain/subtitle`、`api/subtitles.py` | A 的媒体入口更完整；B 更聚焦字幕学习、复杂度低 | 借鉴“媒体时间轴为上下文”，先独立实现最小播放同步，不直接引入 A 代码 |
| 字幕/转录 | 声称字幕、YouTube captions、AI transcription；transcript 相关 schema | SRT/VTT 解析、cue、清洗、统计、无效项处理 | B 的文本导入证据更具体；A 的输入范围更宽但部分待验 | 保留 B 解析口径，研究 A 的时间轴模型 |
| 听力训练 | Listen 入口与播放主线 | 以阅读字幕、朗读为主，未见完整听力模式 | A 更像媒体训练产品，B 尚无媒体播放闭环 | 将听力作为独立产品决策，不因“功能对齐”立即开发 |
| 跟读/口语 | Echo/Shadowing、录音、Azure/对齐依赖，完整闭环待验 | 本地 TTS；未发现录音评分闭环 | A 的训练类型更丰富，B 的离线朗读更可控 | 借鉴训练流程，重新设计本地/可选云评分边界 |
| 听写 | Dictation 数据/feature 声称 | review 当前以 spelling/meaning 为主 | A 的听写语境更强；B 的复习数据模型更透明 | 先验证学习价值和输入流程，再决定数据扩展 |
| 词汇 | vocabulary/context/review schema，README 声称词库/Anki | `learning_item`、`word_sense`、`context_ref`，去重和快照已实现 | B 在本地持久化和来源追踪上扎实；A 的导出/生态更宽 | 保留 B 数据事实，借鉴 A 的导出/上下文呈现思想 |
| 释义/翻译 | 多 AI SDK 声明，具体供应商行为待验 | Qwen 网关、本地 IPA、缓存、用户确认 | B 的云端边界更明确；A 的供应商选择更丰富 | 不直接照搬多供应商；先定义 provider port |
| 发音 | Azure pronunciation 声称，需实机验证 | IPA 本地词典 + macOS `say`，`app/integrations` | B 离线基础好，A 可能有评分深度 | 保留本地优先，评分作为可插拔后续能力 |
| SRS | reviews schema，算法与验证待核 | `review_attempt` 不可变、`review_state` 投影、跨日期规则 | B 的规则可追溯性较强；A 的训练组合可能更丰富 | 以 B 复习事实模型为基线，比较算法而非表面页面 |
| AI 教师 | OpenAI/Anthropic/Google 依赖声明 | Qwen-only，send-plan、SSE、费用、保存确认 | B 的隐私/成本流程更明确；A 的模型选择宽 | 借鉴抽象能力，不复制供应商耦合 |
| 学习记录 | schema 有训练/同步状态 | progress API、学习统计和继续位置 | 两者均有持久化方向，B 的单机边界更清楚 | 先定义核心指标，避免统计重复事实 |
| 同步/账号 | optional auth/sync queue | 无账号、单机本地优先 | A 适合多端产品，B 暂不需要 | 明确是否永远单机；不提前引入同步 |
| UI/导航 | Flutter 多 feature、多平台，页面规模大 | 原生 HTML/CSS/JS 单体前端 | A 的组件/状态工具更成熟；B 的学习成本和部署更低 | 借鉴信息架构，逐步拆 B 前端状态，不换栈作为前提 |
| 数据库 | Drift/SQLite、schema 21、多媒体训练实体 | 手写 SQL/SQLite、V7、字幕/词汇/复习/AI | A 功能面大、迁移复杂；B 透明可学、规模有限 | 不迁移表结构；用领域需求驱动增量演进 |
| 离线能力 | 本地媒体/SQLite，但云评分/AI 影响部分功能 | 核心字幕/词汇/复习/IPA/TTS 可本地 | B 离线边界更清晰 | 把离线核心闭环作为 2.0 验收门槛 |
| 测试/维护 | Flutter tests、CI/发布测试多；未运行 | 13 task suites、browser/benchmark；未运行 | 两者都有测试材料，不能仅按数量判质量 | 后续以关键用户流程和数据恢复做真实验收 |
| 许可 | AGPL-3.0 | 需遵循 SceneLingo 自身仓库规则；不能假定兼容 | 直接复用 A 代码有显著合规义务 | 只借鉴思想/流程，代码独立重写；必要时法律审查 |

## 结论

A 的领先项主要是媒体入口、训练类型组合和多平台产品化；B 的领先项主要是本地数据边界、可审计复习历史、字幕语境快照、AI 发送确认和单体可理解性。融合不应以“把 A 的功能表复制进 B”为目标，而应以 B 的数据与隐私基线承载少量经过验证的训练闭环。
