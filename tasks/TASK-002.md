## 1. 功能目标

建立 SQLite 存储层骨架，使后续任务可以在**受控事务**和**可追踪版本**下读写数据：

- 数据库文件位于应用数据目录，启动时检查可读写。
- 迁移机制：有序、前向、版本标记（`PRAGMA user_version` 或等价单一版本号）。
- 迁移失败**停止启动**，保留原库并给出恢复说明，不自动重建、不降级。
- 迁移前自动备份最近 1 份。
- 统一事务工具与仓储基类；启用 WAL、外键约束、忙等待超时。
- 提供连接与事务的健康自检（不暴露细节给前端）。

本任务**只建立机制**，不建业务表（业务表随 TASK-003 起按数据库设计逐张落地）。

## 2. 相关需求编号

- FR-003 本地数据持久化
- NFR-011 可维护性（结构变更可迁移）
- EX-008 本地数据损坏/被占用

## 3. 涉及模块

- `app/core/`：配置中的数据目录解析
- `app/repositories/`：连接管理、迁移执行、事务上下文、仓储基类
- `app/main.py`：启动自检（迁移 → 成功才开放接口）

## 4. 输入与输出

**输入**

- 数据目录路径（来自配置，默认 `~/Library/Application Support/SceneLingo`）。
- 迁移定义（有序列表，每个迁移有唯一版本号与说明）。

**输出**

- 数据库文件 `scenelingo.db`；备份目录 `backups/`（迁移前副本）。
- 启动日志：当前版本、目标版本、迁移结果（成功/失败），不含数据内容。
- 失败时的错误码与用户可读恢复说明（指向备份目录与下一步操作）。
- 测试可用的临时库工厂（不污染真实数据目录）。

## 5. 技术约束

1. 使用标准库 `sqlite3`，手写 SQL；不引入 SQLAlchemy/Alembic/ORM。
2. 每次连接启用：外键约束、WAL 模式、`busy_timeout`（具体值由实现给出并有测试）。
3. 事务边界在服务层显式开启；仓储方法不自行提交，除非是独立只读查询。
4. 迁移前关闭/回滚未完成事务，做一次 WAL 检查点，再进行一致备份（在线备份 API 或检查点后复制）。
5. 备份文件名含时间戳；只保留最近 1 份迁移前备份，超出时删除最旧（仅限本应用创建的备份）。
6. 迁移失败：不继续启动、不回滚已执行迁移记录（SQLite DDL 事务性由迁移包在单个事务内保证）、不删除数据库。
7. 数据库文件权限仅当前用户（`0600`），目录 `0700`。
8. 连接不跨线程共享；请求级连接由依赖注入创建与关闭。

## 6. 实现边界

**做**

- 连接工厂、迁移执行器、版本读取、备份、事务上下文、仓储基类/工具、启动自检、错误码。
- 一个内部自检查询（如 `SELECT 1` 与版本读取），用于启动验证。

**不做**

- 不创建字幕、词条、复习、AI 等业务表（TASK-003 起按 `docs/03` 落地）。
- 不写业务仓储方法。
- 不做用户可见的导入/导出/备份界面（P1）。
- 不做加密数据库（不在需求内）。

## 7. 自动化测试要求

1. 空库启动 → 迁移到目标版本；版本号正确。
2. 已是最新版本 → 不重复执行迁移。
3. 迁移中途抛错 → 启动失败；数据库文件未丢失；错误可读；不自动重建。
4. 迁移前生成备份；备份可打开且版本为迁移前版本。
5. 外键约束生效：插入违反外键的行被拒绝。
6. 事务回滚：事务内抛错后，前后数据无变化。
7. 两个连接并发写：后写者按 `busy_timeout` 等待或返回可分类错误，不静默丢写。
8. 数据库文件权限 `0600`，目录 `0700`。
9. 只读/不可写目录场景：启动失败并给出明确错误，不创建“半个库”。

## 8. 人工验收标准

1. 首次启动后，在数据目录看到 `scenelingo.db`，权限正确。
2. 关闭并重启，版本号不变，日志显示“已是目标版本”。
3. 手动把库文件设为只读后启动，应用拒绝启动并说明原因；恢复权限后正常启动。
4. 制造一次失败迁移（测试用迁移），确认备份存在、原库未被删除、应用未继续提供服务。
5. 查看日志：不含数据内容、不含完整路径以外的敏感信息。
